웹사이트에서 로그인하지 않은 방문자의 요청을 받아 페이지를 만들고 데이터를 처리하는 PHP 런타임에 원격 코드 실행 취약점 두 건이 공개됐습니다. 공격자가 서버의 PHP 처리 과정에 특정 요청을 보내면, 인증 없이 서버에서 코드를 실행할 가능성이 있습니다.

이 취약점들은 **CVE-2026-109618**과 **CVE-2026-109619**입니다. 보안 업계에서 두 건을 묶어 **PHP2Shell**이라고 부르지만, PHP 프로젝트의 공식 공지는 각각의 CVE로 설명합니다. 두 취약점 모두 PHP 코어의 메모리 처리에서 비롯됐지만, 발생 조건과 재현 경로는 다릅니다.

## 한눈에 보기

- **대상:** 웹 요청을 처리하는 PHP 런타임
- **취약점:** CVE-2026-109618, CVE-2026-109619
- **영향:** 취약한 실행 경로에서 인증 전 원격 코드 실행 가능
- **심각도:** 각각 CVSS v4.0 9.2, PHP 프로젝트 기준 Critical
- **수정 버전:** PHP 8.5.12, 8.4.27, 8.3.36, 8.2.35
- **확인 기준:** 2026년 10월 24일 공개된 PHP·CISA·Censys 자료

## PHP2Shell은 무엇인가

PHP는 서버에서 웹 요청을 받아 애플리케이션 코드를 실행하는 런타임입니다. Apache의 `mod_php`, PHP-FPM, `php-cgi`, FrankenPHP, LiteSpeed 등 다양한 실행 방식이 있습니다.

이번 문제는 워드프레스나 특정 플러그인에만 해당하는 취약점이 아닙니다. PHP 요청 처리 단계의 메모리 안전성 문제가 핵심이므로, PHP를 사용하는 CMS나 애플리케이션을 최신화해도 서버의 PHP 런타임이 취약 버전이면 문제가 남을 수 있습니다.

다만 모든 PHP 서버에서 위험이 똑같이 재현되는 것은 아닙니다. PHP 프로젝트는 웹 요청을 처리하는 PHP 설치 전반을 위험 범위로 안내하면서, `mod_php`를 특히 높은 위험의 구성으로 설명했습니다. 실행 방식과 설정에 따라 확인된 공격 경로와 재현 수준에 차이가 있습니다.

## 취약점 두 건은 어떻게 다른가

### CVE-2026-109618: 메모리 부족 처리 중 상태 손상

PHP는 메모리 부족 오류가 발생하면 현재 요청 처리를 중단합니다. 요청 데이터가 완전히 초기화되기 전에 오류가 나면, 종료·정리 과정에서 PHP가 유효하지 않은 메모리 상태를 다시 참조할 수 있습니다. 이런 잘못된 메모리 접근이 원격 코드 실행으로 이어질 수 있습니다.

PHP 프로젝트는 특히 Apache `mod_php`에서 애플리케이션 코드가 실행되기 전 요청 시작·정리 과정으로 악용되는 경우를 검증했습니다. PHP-FPM 등 다른 실행 방식도 위험 범위에 포함되지만, 경로별 재현 수준과 확인 여부는 서로 다릅니다.

### CVE-2026-109619: 해제된 요청 상태를 다음 요청에서 사용

PHP 워커는 설정에 따라 여러 웹 요청을 차례로 처리합니다. 앞선 요청의 메모리는 해제됐는데 워커의 전역 상태가 그 메모리를 계속 가리키면, 같은 워커가 다음 요청을 처리할 때 오래된 상태를 읽을 수 있습니다. 이를 **use-after-free(해제 후 사용)**라고 합니다.

PHP와 연구자들은 세션 업로드 진행률 등 특정 처리 경로에서 이 문제가 원격 코드 실행으로 이어질 수 있음을 확인했습니다. 이 취약점도 모든 서버 설정에서 같은 방식으로 작동한다고 볼 수는 없습니다.

두 문제는 모두 메모리 안전성 결함이지만 원인은 다릅니다. 하나는 **메모리 부족 오류 뒤 잘못된 요청 상태를 정리하는 과정**, 다른 하나는 **요청이 끝난 뒤에도 남은 이전 요청의 메모리 상태**가 핵심입니다.

## 발견과 공개 과정에서 AI가 맡은 역할

PHP 프로젝트는 2026년 10월 20일 유지관리자와 일부 대응 조직에 사전 안내를 하고, 10월 21일 수정 버전을 공개했습니다. 취약점 정보가 공개 전에 유출되면서 공개 일정이 앞당겨졌다고 Censys는 정리했습니다.

발견 과정도 주목받았습니다. OpenAI는 Patch the Planet 협력 과정에서 Calif가 GPT-5.6 Sol을 활용해 중대한 PHP 결함을 찾았고, Wiz도 두 취약점을 독립적으로 발견해 신고했다고 발표했습니다. 수정과 배포는 PHP 유지관리자가 주도했으며, 연구자와 인프라·보안 업체들이 패치 검증과 대응 준비에 참여했습니다.

따라서 이 사건을 “AI가 두 취약점을 혼자 발견했다”고 쓰면 부정확합니다. 공개된 자료가 확인하는 것은 AI를 활용한 취약점 연구, 독립적인 연구팀의 발견, PHP 유지관리자의 수정, 여러 조직의 공개 전 대응이 함께 진행된 과정입니다.

## 악용 시도와 실제 침해는 구분해야 한다

공개 시점과 악용 정황은 빠르게 바뀌고, 현재 공개된 분석도 일치하지 않습니다. CISA는 10월 21일 공지에서 당시까지 악용을 관찰하지 못했다고 밝혔습니다. 이후 Censys가 10월 23일 갱신한 분석에서는 Amazon이 사전 공개 시기의 시도와 공개 후 활동을 근거로 CVE-2026-109618의 광범위한 악용을 언급한 반면, Dataminr와 캐나다 사이버보안센터는 관측된 활동이 주로 스캔·탐색이며 확인된 침해는 없다고 평가했습니다. VulnCheck 센서가 관측한 CVE-2026-109618 시도 한 건은 실패한 것으로 기록됐습니다.

**악용 시도가 보였다는 사실과 실제 서버 침해가 확인됐다는 주장은 다릅니다.** Censys는 10월 23일 기준 두 CVE가 CISA의 알려진 악용 취약점 목록에 없다고 기록했습니다. Censys의 후속 보고 역시 성공한 침해의 규모를 두고 상반된 평가를 함께 소개합니다.

Censys는 PHP2Shell 전용 [공개 대시보드](https://php2shell.censys.com/)를 운영합니다. 로그인 없이 열람할 수 있으며, 취약 버전·수정 버전 서비스의 분포와 브랜치별 패치 진행 상황을 살펴볼 수 있습니다. 화면의 `Affected`, `Patched`, `All PHP` 필터와 PHP 브랜치 선택 메뉴로 공개 인터넷에서 관측된 범위를 나눠 볼 수 있고, 스캐너 관측 그래프는 시간 단위로 갱신됩니다.

다만 이 페이지는 사이트 주소를 넣어 안전 여부를 판정해 주는 **개별 사이트용 취약점 검사기**가 아닙니다. Censys 스캐너가 관측한 PHP 응답과 보고 버전을 집계한 현황판입니다. 같은 서비스가 여러 번 관측될 수 있고, 버전 정보가 감춰진 서비스는 따로 분류되지 않을 수 있으며, 배포판의 백포트 수정은 공개된 버전 문자열에 드러나지 않을 수 있습니다. 따라서 표시된 수치는 고유 웹사이트 수나 확정된 취약 서버 수로 읽으면 안 됩니다. 대시보드는 인터넷 노출 추세를 파악하는 보조 자료로 활용하고, 내가 관리하는 서버의 수정 여부는 실제 웹 런타임과 공급자 보안 공지로 확인해야 합니다.

무료 온라인 검사기를 사용할 때도 검사 방식과 한계를 먼저 살펴야 합니다. 버전 배너만 확인하는 방식은 버전이 숨겨졌거나 프록시·CDN 뒤에 있는 서버를 놓칠 수 있고, 능동적인 요청을 보내는 검사 도구는 서비스에 영향을 줄 수 있습니다. 타인의 시스템을 허가 없이 검사하지 말고, 취약점 재현이나 익스플로잇을 포함한다고 주장하는 출처 불명의 도구를 운영 서버에 실행하지 않는 편이 안전합니다. 운영자라면 먼저 호스팅 업체나 패키지 공급자에게 적용된 수정 사항을 확인하고, 승인된 점검 절차로 실제 PHP-FPM·Apache 모듈·컨테이너 런타임을 확인하는 것이 정확합니다.

## 수정 버전과 운영자가 확인할 점

PHP 프로젝트가 공개한 수정 버전은 다음과 같습니다.

- **PHP 8.5:** 8.5.12
- **PHP 8.4:** 8.4.27
- **PHP 8.3:** 8.3.36
- **PHP 8.2:** 8.2.35

Linux 배포판이나 호스팅 업체는 수정 사항을 기존 패키지에 백포트할 수 있습니다. 이 경우 표시되는 PHP 버전 문자열이 PHP 공식 수정 버전과 다를 수 있으므로, 버전 숫자만 비교하지 말고 공급자의 보안 공지와 패키지 변경 이력에서 두 CVE의 수정 여부를 확인해야 합니다.

PHP 프로젝트는 8.1 이하 브랜치에 일반 릴리스를 제공하지 않지만, 7.4·8.0·8.1에 대해서는 직접 빌드하는 사용자를 위한 최소 소스 백포트를 공개했습니다. Linux 배포판이나 장기 지원 업체가 별도로 패치를 백포트했을 수도 있으므로, 해당 업체의 보안 공지를 확인해야 합니다. Censys는 5.4~7.3 브랜치를 지원 종료 상태로 분류하고 업스트림 수정판이 없다고 안내했습니다.

`php -v`가 보여주는 CLI 버전과 실제 웹 요청을 처리하는 PHP-FPM·Apache 모듈의 버전이 다를 수 있습니다. 웹 서버나 호스팅 관리 화면에서 요청을 처리하는 런타임을 확인하고, 공급자가 제공하는 수정 패키지를 적용한 뒤 해당 런타임의 작업 프로세스가 새 버전으로 재시작됐는지 점검해야 합니다.

![PHP 브랜치별 수정 버전과 오래된 브랜치의 확인 기준](/assets/posts/php2shell-rce/patch-branches.svg "PHP 8.2–8.5 수정 버전 및 이전 브랜치 대응")

PHP 프로젝트는 업데이트를 완전한 해결책으로 안내합니다. 즉시 업데이트하기 어려운 경우 공식 권고의 임시 완화책을 검토할 수 있지만, 각 완화책은 특정 공격 경로만 줄이며 취약점을 제거하지는 않습니다. CISA는 PHP 설치 위치를 전수 확인하고 인터넷에 노출된 시스템부터 패치하며, 업데이트할 수 없는 지원 종료 시스템은 수정 전까지 오프라인으로 두도록 권고했습니다. 패치 뒤에도 PHP 워커가 셸을 실행하거나 외부 도구를 내려받는 등 평소와 다른 동작이 있었는지 살펴야 합니다.

웹사이트 운영자가 아닌 방문자가 브라우저에서 직접 PHP 버전을 고칠 수 있는 것은 아닙니다. 호스팅 서비스를 이용한다면 공급자의 PHP 패치 적용 여부를 확인하고, 직접 서버를 운영한다면 웹 요청을 처리하는 PHP-FPM·Apache 모듈·컨테이너 런타임이 실제로 수정됐는지 점검해야 합니다. CLI의 `php -v` 결과만으로 웹 서버가 사용하는 런타임까지 확인했다고 단정할 수는 없습니다.

## 별도 후속 공지: CVE-2026-115560

PHP 프로젝트는 10월 23일 세션 업로드 진행률 기능과 관련한 **별도의 잠재적 RCE 경로**를 안내하고 CVE-2026-115560을 예약했습니다. 이 문제는 세션 업로드 진행률이 활성화돼 있고, 애플리케이션이 `session.serialize_handler`를 특정 방식으로 바꿨다가 요청 중 다시 변경하는 드문 조합에서 발생할 수 있다고 설명했습니다.

PHP는 다음 정기 릴리스 전까지 `session.upload_progress.enabled=0`을 임시로 권고했습니다. 런타임에서 세션 직렬화 핸들러를 바꾸지 않는 애플리케이션은 해당 기능을 계속 사용할 수 있다고 안내했습니다. 이 후속 이슈는 PHP2Shell의 두 CVE와 별개이며, 전체 기술 권고와 수정 버전은 다음 정기 릴리스에 공개될 예정입니다.

## 정리하며

PHP2Shell은 웹 애플리케이션의 코드만 점검해서는 서버의 위험을 파악하기 어렵다는 점을 보여줍니다. PHP 런타임과 실행 방식, 공급자의 패치 상태도 함께 확인해야 합니다. 특히 PHP는 웹 애플리케이션과 여러 관리형 서비스에 포함되어 있어, 조직이 직접 설치한 서버 외에 호스팅·컨테이너·외부 솔루션의 런타임도 점검 대상입니다.

이번 이슈에서는 취약점 공개와 패치 사이의 시간이 짧았고, 공개 후 악용 상황을 둘러싼 보고도 엇갈렸습니다. 그래서 확인된 사실과 추정, 악용 시도와 성공한 침해를 구분해 전달하는 일이 중요합니다. 패치 버전을 적용하고 작업 프로세스를 재시작한 뒤, 외부 노출 여부와 로그를 함께 살피는 것이 현재 운영자가 취할 우선 조치입니다.
